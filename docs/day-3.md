# Day 3 — Scaling

Welcome to Day 3. Today we look at how to scale both the workloads and the cluster itself.

GKE provides three scaling mechanisms, and they work together:

- **Horizontal Pod Autoscaling (HPA)** — more/fewer *pods* (handles load)
- **Vertical Pod Autoscaling (VPA)** — bigger/smaller *pods* (right-sizes requests)
- **Cluster Autoscaling (CA)** — more/fewer *nodes* (makes room for the pods HPA/VPA create)

HPA/VPA create demand; CA supplies the nodes to satisfy it.

> Both **Cluster Autoscaling** (the `general` node pool's `autoscaling { min 1, max 3 }` in
> `node_pool.tf`) and **VPA** (`vertical_pod_autoscaling` in `cluster.tf`) are already enabled in
> Terraform. Today is about *using* them.

## Horizontal Pod Autoscaling

We scale the **frontend** based on the number of requests it receives, using the request-count
metric exported by the external load balancer that the Ingress creates.

First install the stackdriver adapter, which exposes Cloud Monitoring metrics to the HPA:

```bash
export PROJECT_ID=$(gcloud config get-value project 2>/dev/null)
envsubst < k8s-manifest/scaling/stackdriver-adapter.yaml | kubectl apply -f -
```

Then create the HPA. The load balancer's `forwarding_rule_name` is generated by GKE and can't be
hardcoded, so we read it from the Ingress annotation at apply time and substitute it:

```bash
export FORWARDING_RULE=$(kubectl get ingress frontend-ingress -n app \
    -o jsonpath='{.metadata.annotations.ingress\.kubernetes\.io/forwarding-rule}')
envsubst < k8s-manifest/scaling/hpa.yaml | kubectl apply -f -
```

### Testing it — drive load *through the load balancer*

This is the important part. The HPA scales on the **external load balancer's** request count. The
in-cluster `loadgenerator` calls the frontend at `frontend:80` (the ClusterIP Service), so its
traffic **never traverses the load balancer** and won't move the metric. To make the HPA scale, you
must send traffic to the **Ingress IP** so it goes through the LB:

```bash
kubectl get ingress -n app
```

> Note the IP address of the Ingress.

Send load to it with `hey`:

```bash
hey -n 1000 -c 10 http://<ingress-ip>
```

In another terminal, watch the HPA react:

```bash
kubectl get hpa -n app
```

As the LB request count climbs above the target, `REPLICAS` increases toward `maxReplicas`.

## Cluster Autoscaling

Cluster Autoscaler adds worker nodes when pods can't be scheduled for lack of resources, and removes
nodes when they sit underutilized. It operates per node pool — here, the `general` pool (1–3 nodes).

First note how many general nodes are running:

```bash
kubectl get nodes -l cloud.google.com/gke-nodepool=general
```

Create a deployment with real resource requests and scale it beyond the current capacity, so some
pods can't fit:

```bash
kubectl create deployment nginx --image=nginx:1.16
kubectl set resources deployment nginx --requests=cpu=500m,memory=500Mi
kubectl scale deployment nginx --replicas=12
```

Some pods will be `Pending` (no room on the current nodes):

```bash
kubectl get pods -l app=nginx
```

Wait a bit, then check the node count again — the autoscaler adds nodes (up to the pool's max of 3):

```bash
kubectl get nodes -l cloud.google.com/gke-nodepool=general
```

Clean up:

```bash
kubectl delete deployment nginx
```

Things to know:

- CA only acts on pods that are `Pending` **because of insufficient resources**, which is why the
  workload must set `requests`.
- **Scale-down is deliberately slow** (~10 min of underutilization) to avoid thrashing — don't
  expect the extra nodes to disappear immediately after deleting the deployment.
- `max 3` on `e2-standard-2` is the ceiling; the demo won't scale past it.

## Vertical Pod Autoscaling

VPA right-sizes a workload's CPU/memory **requests** based on observed usage. For this demo we run
it in **recommendation mode** (`updateMode: "Off"`) — it only reports suggestions and doesn't
disrupt pods.

Create the VerticalPodAutoscaler:

```bash
kubectl create -f k8s-manifest/scaling/vpa.yaml
```

After a while, check the recommendation:

```bash
kubectl get vpa -n app
kubectl describe vpa -n app          # shows Target / Lower / Upper bound
```

> **Caveat — don't combine VPA `Auto` with HPA on the same resource metric.** If VPA is changing a
> workload's CPU/memory requests while an HPA scales on the *utilization* of those same requests,
> they fight and oscillate. Recommendation mode (`Off`) is always safe; if you switch a workload to
> `Auto`, pick one that isn't under a CPU/memory-based HPA.

## Summary

```
HPA  → more/fewer PODS    (load)
VPA  → bigger/smaller PODS (right-size)
CA   → more/fewer NODES    (capacity)
```
